# AGENT.md — ASUMI.Producer.RabbitMQ.Service

Справочник по подключениям к инфраструктуре для агента, который правит этот
репозиторий. Здесь нет паролей: секреты лежат в соседнем репозитории и в
переменных окружения, и приводить их здесь — значит утечь их в git.

Обновлён: 2026-11-12. Жизнеспособность стека по этой дате: все проверки
смоук-теста пройдены. Из внешних целей Prometheus закрыты обе dev-цели
(`172.18.16.1` — продюсер и nanocad не запущены на dev-машине, это норма)
и прод-машина `10.54.0.46` (реальная проблема).

Стек, дашборд, ACL и правила alert'ов живут в соседнем репозитории
`RabbitMQ.Consumer.PilotICE.Infra`. Там же — разбор экспорта метрик:
`METRICS-HANDOFF.md` в этом репозитории описывает, что именно Prometheus должен
видеть от этого сервиса, и там же перечислено, что нельзя ломать.

## 1. RabbitMQ

AMQP, без TLS. Топология — quorum-очередь на трёх узлах.

| Параметр | Значение |
|---|---|
| Хост (пилот) | `172.18.28.118` — стек внутри WSL2 на машине `NSK-NA02` |
| Хост (прод) | ВМ со стеком, `nsk-na02`; адрес уточнить у владельца инфраструктуры |
| Порт | `5672` (AMQP) |
| Virtual host | `/` |
| Учётная запись | `NSK-ASUMI-PRODUCER` |
| Обмен | `asumi.exchange`, topic, durable |
| Очередь | `asumi.queue`, quorum, durable, `x-message-ttl = 300000` |
| Routing key | `asumi.json` |

Продюсер на Windows-машине `nsk-sapp01` (`10.54.0.46`).

### Пароль

Берётся не из `appsettings.json` (там пустая строка), а из переменной
окружения `RabbitMQ__Password`. Приоритет: **Machine scope выше User scope**, и
это осознанно — машинную переменную читает и служба, и интерактивный сеанс.
Дальше по цепочке: конфигурация (`RabbitMQ:Password` в
`appsettings.Production.json` или аргументы командной строки). Точное место
разбора — `Hosting/PasswordResolver.cs`, там же константа `EnvVarName`.

На стороне инфраструктуры пароль лежит в
`RabbitMQ.Consumer.PilotICE.Infra/rabbitmq/secrets/rabbitmq.env`
(`RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS`).

### Management UI

Порт `15672` намеренно слушает только `127.0.0.1` на стороне стека: снаружи
он закрыт, единственный путь — SSO-edge `https://nsk-na02:8443`.

### Стоит знать

- **`x-message-ttl = 300000` — это временно.** Пока нет потребителя, сообщения
  истекают через пять минут и уходят в `dead-letter.queue`. Это ожидаемо, но
  означает, что «успешно опубликованный» файл ещё не обработан. TTL снимут
  вместе с консьюмером; до этого момента менять TTL не надо.
- `PublishConfirmTimeoutSeconds = 5` — публикация подтверждается брокером, и
  файл переносится в `processed` только после подтверждения. Это правило
  нарушать нельзя.
- Учётные записи, которые есть в брокере: `NSK-ASUMI-PRODUCER`, `portal`,
  `rmuser`, `user`. Первые две — наши, последние — служебные.

## 2. Loki

Push API, HTTP, **без аутентификации**: кто достучался, тот и пишет, и читает
все логи. Ограничение только по источнику.

| Параметр | Значение |
|---|---|
| URL (пилот) | `http://172.18.28.118:3100` |
| URL (прод) | ВМ со стеком, `nsk-na02`; порт `3100`, TLS нет |
| Путь | `POST /loki/api/v1/push` |
| Метка `job` | `ASUMI.Producer.RabbitMQ.Service` |
| Метка `service_name` | `ASUMI.Producer.RabbitMQ.Service` |
| Retention | `168h` (7 суток) |

Значения берутся из секции `Loki` в `appsettings.json`; там же `Job`,
`ServiceName`, `BatchSize`, `FlushPeriodSeconds`, `TimeoutSeconds`,
`QueueCapacity`.

### Формат записи

Строка лога — logfmt с полями `level`, `cat` и `msg`, а в конце JSON с
`SourceContext`, `cat` и `Service`. Поле `cat` — фильтруемое: `system`, `data`,
`config`. Неизвестный источник попадает в `system`, чтобы запись не терялась
из фильтра.

Запрос в Grafana (LogQL):

```
{job="ASUMI.Producer.RabbitMQ.Service"} | cat="system"
{job="ASUMI.Producer.RabbitMQ.Service"} | cat="data" | level="ERR"
```

### Стоит знать

- **Файл сокета Serilog в `appsettings.json` не настроен.** Отправка идёт
  через собственный `Observability/LokiSink.cs`. Пока Loki доступен, это
  незаметно; когда он недоступен, записи копятся в очереди сокета
  (`QueueCapacity`), и при переполнении отбрасываются, а узнать об этом можно
  только из `SelfLog`.
- Порт Loki публикуется на `0.0.0.0`, потому что приложение шлёт логи по сети.
  Это единственный порт стека, доступный с машины продюсера, и он не имеет
  аутентификации — обращаться с ним надо аккуратно.

## 3. Redis

**Этот сервис Redis не использует.** В исходниках нет ни одной ссылки на
Redis: ни в `appsettings.json`, ни в `.csproj`, ни в коде. Ниже — параметры
окружающего стека, на случай если понадобится диагностика или соседняя
задача.

| Параметр | Значение |
|---|---|
| Порт | `6379`; TLS через edge — `6380`; Sentinel — `26379` |
| Учётные записи | `application` (полный доступ), `NSK-REDIS-SERVICE-RO` (только чтение), `exporter`, `replication`, `sentinel`; `default` — выключен |
| Пространство имён | `NSK-REDIS-SERVICE-RO` ограничена `Id_CustContracts:*` и набором команд только на чтение |
| Пароли | `RabbitMQ.Consumer.PilotICE.Infra/redis/secrets/` — `application_password`, `sentinel_password`, `redisinsight.env` |

Топология: `redis-primary` — мастер, `redis-replica` — слейв, три Sentinel
следят за кворумом. **Имена контейнеров обязаны совпадать с ролями** — смоук-тест
проверяет, что мастер именно `redis-primary`. Если мастер был недоступен,
Sentinel может провести failover и объявить мастером `redis-replica`; тогда
роли надо вернуть штатным `SENTINEL FAILOVER redis-primary`, а не руками.

### Устойчивость AOF: не убирайте `aof-load-corrupt-tail-max-size`

В `redis/config/common.conf` стоит `aof-load-corrupt-tail-max-size 8192`. Это
не украшение: если Redis падает во время записи, хвост AOF остаётся залитым
нулями, `aof-load-truncated yes` его не съедает, и без этой опции Redis
отказывается стартовать навсегда. Это уже происходило дважды: 2026-10-20
(хвост 793 байт на мастере) и 2026-11-12 (1672 байта на реплике) — оба раза
контейнер уходил в бесконечный перезапуск.

Диагноз в одну строку — это лог контейнера: `Bad file format ... at offset N`,
и Redis сам называет минимальный подходящий размер хвоста. Сравнение со лимитом
**строгое**: предложенное значение (например, 793) в опцию ставить нельзя, надо
больше (рабочее 1024, теперь стоит 8192 с запасом). Хвост больше лимита по-прежнему
останавливает старт, так что повышение не прячет реальную порчу.

Перед правкой конфига снимайте бэкап volume'а: `/var/lib/docker/volumes/
monitoring_redis_{primary,replica}_data/_data`.

Именование учёток: `NSK-<система>-<роль>`, суффикс `-RO` означает «только
чтение». У Redis две роли в этом смысле: `application` — сервисная, работа с
данными; `NSK-REDIS-SERVICE-RO` — контрактный доступ на чтение.

## 4. Метрики

Prometheus забирает метрики по HTTP.

| Параметр | Значение |
|---|---|
| Endpoint | `http://<адрес машины>:9101/metrics` |
| Цель (пилот) | `172.18.16.1:9101` — сторона Windows в WSL, job `asumi_producer` |
| Цель (прод) | `10.54.0.46:9101` — `nsk-sapp01`, job `asumi_producer` |
| Метки | `docker_host`, `environment` (`development` / `production`) |

Ключевые метрики: `asumi_producer_rabbitmq_connected` (0 или 1),
`asumi_producer_files_published_total`, `asumi_producer_files_failed_total`,
`asumi_producer_files_pending`, `asumi_producer_last_publish_timestamp_seconds`.

### Состояние внешних целей (на 2026-11-12)

- `172.18.16.1:9101` — **dev-машина** (Windows-сторона WSL). Продюсер там
  запускают вручную во время разработки, поэтому порт закрыт, когда сервис
  никто не стартовал, — это норма, а не авария. Пинг в сторону Windows
  использовать как индикатор нельзя: ICMP на её адаптерах всегда блокирован
  firewall'ом (профиль Public).
- `172.18.16.1:9317` (`nanocad_metrics`) — та же dev-машина, экспортёр также
  запускается по необходимости. Сейчас пакет не доходит до порта
  (`context deadline exceeded`), но и это следствие «сервис не запущен».
- `9105` — из конфига Prometheus убран совсем, цели нет.
- `10.54.0.46:9101` (`nsk-sapp01`) — не отвечает; AMQP-соединений из
  продакшн-машины не было ни разу. В отличие от dev-цели, это реальная
  проблема, а не «разработчик не запустил».

### Обязательное условие на Windows

`MetricsServer` работает поверх `HttpListener`, и порт должен быть зарезервирован
за учётной записью службы, иначе `Start()` бросает access denied:

```
netsh http add urlacl url=http://+:9101/ user="DOMAIN\user"
```

Резервация должна закрывать путь, а не только корень: префикс, который
регистрирует сокет, — `http://+:9101/metrics/`, поэтому зарезервировать нужно
`http://+:9101/`. На текущей машине резервация уже есть и выдана
`NSK-NA02\olegus`.

Порт `9101` должен быть открыт брандмауэром Windows для адреса машины с
Prometheus и только для него. Сейчас это правило есть для адреса WSL.

Случай отсутствия резервирования выглядит неприятно: `StartAsync` бросает
исключение, и если его не поймать, не поднимется вся служба целиком. Либо
разрешите URL заранее, либо оберните `_server.Start()` в try/catch и пишите в
лог через `ILogger` — метрики не должны ронять службу.

## 5. Ограничения доступа к портам

Обе цепочки ACL живут в `DOCKER-USER`, а не в `ufw`/`INPUT`: правило `ufw`
не видит трафик к опубликованному порту контейнера, потому что он
перенаправляется и до INPUT-цепочки хоста не доходит. INPUT при этом не
трогается, так что правило не может оборвать SSH-сеанс.

Списки источников — в `ansible/inventory/group_vars/all.yml`:

```yaml
rabbitmq_allowed_cidrs:
  - 10.54.0.46/32      # продюсер на nsk-sapp01
  - 172.18.16.0/20     # только для пилота в WSL2
  - 172.18.0.0/20      # только для пилота в WSL2

loki_allowed_cidrs:
  - 10.54.0.46/32      # продюсер на nsk-sapp01
  - 172.18.16.0/20     # только для пилота в WSL2
  - 172.18.0.0/20      # только для пилота в WSL2
```

Записи `172.18.*` относятся только к пилотному развёртыванию внутри WSL2:
подсеть WSL NAT не маршрутизируется из сети, поэтому извне эта запись не
сработает. **На обычной ВМ их убрать.**

Списки ведутся раздельно нарочно: AMQP-порт и порт Loki — разные сервисы, и
одному из них рано или поздно понадобится адрес, которого у другого нет.

## 6. Что нельзя ломать

Подробности — в `METRICS-HANDOFF.md`, раздел 6. Коротко:

- **Файлы публикуются байт в байт.** Никаких `Encoding.UTF8.GetString` и прочих
  декодирований: файлы приходят в UTF-16LE, и уже была ошибка, при которой
  3414 байт превращались в 1996.
- **Не менять настройку Serilog.** Логика Loki и файлового сокета работают,
  панель логов в Grafana уже показывает их.
- **Не перемещать файл в `processed`, пока публикация не подтверждена** —
  иначе потеряются сообщения при сбое.
- **Не включать принудительную смену паролей** в роли `portal_user` инфраструктуры
  без явной договорённости: слепой сброс блокирует людей при каждом прогоне.

## 8. Как проверить, что связь есть

1. **AMQP:** в Grafana плитка `RabbitMQ` на дашборде ASUMI должна быть зелёной;
   метрика `asumi_producer_rabbitmq_connected` равна 1. На стороне брокера:
   `rabbitmqctl list_queues name messages consumers` — у `asumi.queue` должны
   появиться сообщения.
2. **Логи:** панель `ASUMI Producer logs (Loki)` на дашборде ASUMI, фильтр
   `Категория` — `system`, `data` или `config`.
3. **Метрики:** `curl http://<адрес>:9101/metrics` с машины продюсера должен
   отдать текст с `asumi_producer_`.
4. **Публикация:** метрика `asumi_producer_files_published_total` растёт, а в
   логах видны строки `Published ... to exchange asumi.exchange`.

Отдельно: **журнал «Published» не доказывает доставку.** Приложение ждёт
подтверждения от брокера, но при отказе брокера запись в логе всё равно
появляется. Проверять доставку надо по счётчику в брокере.
